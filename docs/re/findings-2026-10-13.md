# Findings, 2026-10-13 (offline analysis session)

## Live client log (`Client.txt` from real play, read only)
- `scripts/re/clientlog_entries.py`: per-entry timelines (area, seed, first log lines with ms offsets).
- `scripts/re/clientlog_terrain.py`: (area, level, seed, tile hash, doodad hash) test vectors into `runtime/terrain-vectors.tsv`. That gives 1,744 vectors across 260 areas, for the M5 generator.
- **Towns and hideouts always use seed 1** (all 27 seen). Implemented as `WorldArea::fixed_seed`.
- With seed 1 the tile hash is constant (`G1_town` → `892597717`), but the doodad hash varies between visits, so doodads depend on state (quests and similar). Check for us: loading `G1_town` should log `Tile hash: 892597717`.
- A live `G1_1` entry follows the same client log order as ours up to `[SCENE] Set Source [The Riverbank]`. Live then shows:
  - `Joined guild …` and `InstanceClientSetSelfPartyInvitationSecurityCode = 0`, both server messages we don't send;
  - `Tried to SetExtraActivationRangeAroundTile() after level generation was complete` (`0x141d12f40`). This is client-side: it widens the activation range of terrain tiles (the 0x38-byte records at terrain +0x28) for objects that load late. It's harmless noise and not a server message;
  - the washed-up intro dialogue ("Wounded Man: By the First Ones! You're alive!").

## Client packet classes
- `scripts/re/packet_layout.py <opcode…>` lists serializer and deserializer write/read calls for classes whose constructor stores the opcode at +8.
- Mapping vtables to opcodes over all of `.rdata` gives 306 serializer-shaped vtables and 185 opcodes: `packet_classes_0.5.5e.json` (opcode → vtables, both directions; slot 1 serialize, slot 2 deserialize).
- Client→server, seen in game:
  - `0x63` WASD direction: `u8, varint x, varint y, u8[3]`. The vector is about 180 long; (127, 127) is a diagonal and (0, 0) means stop.
  - `0x1c`: 10 Hz, `u8, u32` (heartbeat or tick; no reply yet).
  - `0x62`: `u8, u8, [u32, u32]`.
  - `0xbc`: bytes.
  - Also seen once each: `0x23d`, `0x351`, `0x357`, `0x14c`, `0x13d`, `0x1ff`, `0x221`, `0x2e8` (UI and settings).

## Rendering ("grey Riverbank")
- The town renders (the player was off-map). The Riverbank shows grey with a black bar, so the problem is area- or position-specific.
- Entity height is never sent by the server. `0x141de5390` (Positioned "get position height") samples the terrain at the world position (`0x141d0d420`/`0x141d0d650`) unless an explicit height is set (+0x440/+0x48c, Positioned flags0 bit 2).
- Riverbank env (`Metadata/EnvironmentSettings/Gallows/1_1.env`):
  - camera far plane 3639;
  - clouds that fade only within 500 units of the player (`clouds_fade_radius`);
  - rain attached to the player.

  So the start position matters more than in town.
- **Spawn position**: G1_1's topologies are `Metadata/Terrain/Gallows/Act1/1_1/Graphs/intro_{1..6}.tgr`. Their nodes name rooms: `tutorial1_river` (the washed-up start), `entrance`, `source`/`sink`, `lumberjack`. Placement comes from the generator (M5).

  Until then, the DLL dumps the client's generated tile grid (`terrain_tiles.txt`, written when the player spawns: per tile the raw 0x38-byte record plus any reachable `Metadata/`/`Art/` paths). That shows where the start room was placed.

## Spawn and grey screen (resolved)
- Grey view with a black bar = the player stands on a non-walkable spot: filler tiles such as `driedriver_fill` outside the map, or the centre of `Intro_Tree_01` in rotated layouts (`ZombieIntroFeature_Reorient_*`). On walkable ground the area renders.
- Tile array: terrain object embedded in the world at +0x8d0; size in tiles at +0x18 (x) and +0x20 (y); 0x38-byte tile records at +0x28 in row-major order (`y * w + x`, as in `0x141d12f40`). Record +8 → tile object, whose +8 is the `.tdt` path. The tile hash is at world +0x114 and the doodad hash at +0x118 (`0x14167b270`). Area kinds 0x20/0x21/0x23 (world +0x98 → +0x1b4) are world-map loads that log no hashes.
- Test driver:
  - `scripts/test-run.sh` (needs Steam running) launches the client; the DLL `auto_keys` logs in;
  - `poe-hook.keys` takes key presses at any time (`0x0d`, `0x57:800`);
  - `scripts/shot.sh` takes a screenshot of the game monitor (Spectacle).
  - After login a notice with the account name and an OK button appears (to be explained by the login analysis).

## Player model not drawn (resolved)
**Cause:** InitialState's varuint (world +0x11c, the server frame length in ms) was 0. The world update `0x1421302c0` gives each queued frame `dt = frame_ms / 1000`, so every entity update ran with dt = 0: no animation, no fade-in, so models stayed invisible while labels and lights showed. A server-sent waypoint behaved the same, so it was not player-specific. With `frame_ms = 33` the player, NPC models and the town render, and the first-entry grey view is gone. How it was found: the frame drain's dt for the game world was always 0 (DLL hook on `0x1421306c0`), dt comes from the frame queue values, and those are recorded from world +0x11c, which InitialState overwrote with 0.

Earlier observations, kept for reference. State of the player entity in town (DLL `dump_object_types`, 5 s after spawn):
- Awake: entity +0x8c = +0x8d = 0x0c (bit 2: in the wake/update set).
- Updated every simulation frame. The world runs in **frame mode** (world +0x661 = 2): the frame drain `0x1421306c0` applies queued `0x2f7`/`0x2f4` packets, and `0x1421370f0` updates entities inline: component vfunc +0x50 per component, then `0x141e7d7f0(entity + 0x58, dt)`. It does not go through `0x141e71090`. The player gets about 30 updates per second. Tick markers are queued only while world +0x661 and +0x86a are set; each marker records world +0x11c, which `0x2f5` (u8, world vfunc +0x178) sets.
- Not paused: world +0x868 = 0.
- Rendering enabled: Render component (getter `0x140150cb0`, looked up by name) +0x39a = 0. GEAL `EnableRendering` (lambda `0x141923f80`) clears +0x39a, then `0x1416a9810` shows (vfunc +0x60) or hides (+0x58) the AO's scene node, depending on +0x39a and entity +0x8d bit 0. Calling `0x1416a9810` from the DLL changes nothing.
- No NaN or inf floats in any of the 13 components; `0x7fffffff` sentinels only.
- The Animated AO exists. Animation index 0 (`idle_01`, the only entry in `OneRig.amd`) can be started with Animated bit 3 (`POE_ANIM=0`), with no visible effect.

Not yet checked: what the AO's skinned mesh and its attachments (`DexFour.ao`: RangerBody/Boots/Gloves/Hair via `AttachedAnimatedObject`) need to load, and whether resources for server-created objects need a preload list (AreaInfo +0x70 is a `u16`-count `u32` vector; in PoE1 it was the preload list).
