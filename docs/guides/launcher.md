# Launcher

The player launcher: one small desktop program (Tauri 2 with a Svelte 5 UI) that does what `cargo xtask deploy-client` and `run-client` do for the developer ([setup.md](setup.md)), without this repository. Repo [Poe2Launcher](https://github.com/Distorbed678/Poe2Launcher) (public), the submodule `modules/launcher`. Its own README covers development; this page covers using it and how it fits the server.

What it does. The window is a sidebar (the brand, the **game version** picker, five pages, your account and *About*) and the page. The look follows the shared design tokens ([Look and motion](#look-and-motion)).
- **Game version picker (top of the sidebar):** a list that opens below the box, as wide as the sidebar: the private-server versions this launcher supports and *Official (read-only)*, each with *installed* / *not installed*. The choice drives the install folder and depots, file verification, the hook deploy, Play, the server-release filter of *Create a server* and the compatibility of the servers in the list ([below](#game-versions-and-the-official-mode)).
- **Play** (the first page, `#/home`): the selected server (click it to pick another), the big **Play** button and one line of state under it, the *Get ready to play* checklist while something is missing, and the newest news item as a link ([below](#play-and-news)).
- **News:** project news and the selected server's message of the day, a list on the right and the chosen item in full; the sidebar entry counts items newer than the ones you have seen.
- **Servers:** two tabs. *My servers*: your hosted server on top (*Hosted on this computer*: its state, **Start**/**Stop** and **Manage**), then the saved profiles (a name and the cluster's web API address) as compact rows; a row's chevron opens **log in, create an account and log out**, the details, *Check*, *Edit* and *Remove* (a server you still have to log in to opens by itself) (the account part of the former Account page; the token sits in the OS keyring, [../architecture/web-api.md](../architecture/web-api.md)). Admins get **Web admin** ([below](#open-web-admin)); plain `http://` to another machine needs your confirmation first ([below](#plain-http-warning)). *Browse public*: the public server list ([below](#server-browser)). **Add by address** opens a small form; **Create a server** (shown while you host nothing) opens the hosting panel: it downloads the matching `poe-server` release (or takes a local package), sets it up, starts and stops it, streams its log, backs up its database, and adds it to Servers ([below](#host-a-server)).
- **Library:** three tabs. *Game*: downloads the selected client (a pinned private version such as 0.5.5e, or the current official build) from Steam with *your own* Steam login into the launcher's own folder (pause and resume, speed, disk-space check), verifies and repairs it, and the **Client hook** card. *Mods*: the mod cache and the mod browser, per-server mod sets and the server's required mods (Mod sync Off / Ask / Auto), by the `mod.toml` spec ([../../modules/client-hook/docs/mod-manifest.md](../../modules/client-hook/docs/mod-manifest.md); the hook's mod loader loads the enabled ones, never in official mode; see [Mods](#mods)). *Logs*: game logs, the server log and crash dumps ([below](#logs-and-crash-dumps)).
- **Settings:** per-version install folder, hook DLL folder, Proton, **Mod sync** and the mod cache, **Log out of Steam**, theme, window frame, *Minimize the launcher while the game is running*, the desktop entry (Linux AppImage) and launcher updates. **About** (version, supported game versions, disclaimer) is the small link at the foot of the sidebar. Old links (`#/account`, `#/install`, `#/mods`, `#/host`) open Servers (with the hosting panel for `#/host`) and Library.
- **Play:** deploys the hook ([../architecture/client-dll.md](../architecture/client-dll.md)), signs the game in without typing a password, starts it (Proton on Linux, native on Windows).

## Download, install and update

Releases of the launcher are on the [GitHub releases page of Poe2Launcher](https://github.com/Distorbed678/Poe2Launcher/releases) (v0.1.0 is the first, 2026-10-21). Each has the Linux AppImage, the Windows installer, their `.sig` files and `latest.json`.

- **Linux:** download `Poe2.Launcher_<version>_amd64.AppImage`, `chmod +x` it and run it. Keep it where it is: the launcher updates this file in place. (AppImages need FUSE 2 on the system, or start it with `--appimage-extract-and-run`.)
- **Windows:** download and run `Poe2.Launcher_<version>_x64-setup.exe` (per-user NSIS installer, no administrator rights). Windows SmartScreen may warn because the installer is not code-signed (the update signature below is not a Windows code-signing certificate).
- **Updates:** the launcher looks for a newer release when it starts and on Settings, *Updates*, *Check for updates*. When one exists, a badge "Update <version> available" appears in the top bar and Settings shows the version and the release notes. *Download and install* downloads the new AppImage or installer, verifies its signature against the public key built into the launcher (`plugins.updater.pubkey` in `tauri.conf.json`), installs it (Windows: the installer runs in passive mode, with a progress bar and no questions) and restarts the launcher. A failed check (no release yet, repository private, offline) shows "No update info available" quietly; a failed download or signature check shows the error and changes nothing. Updating only works from an installed AppImage or NSIS install, not from a `tauri dev` or plain `cargo build` binary.
- **App identifier:** `org.poe2modding.launcher` (`tauri.conf.json`). It names the window class and the webview's own storage folder, not the launcher's data: the keyring service and the config and data folders are fixed names (`poe2-launcher`, listed under "Data and secrets" in the launcher README), so they do not depend on it.
- The endpoint is `https://github.com/Distorbed678/Poe2Launcher/releases/latest/download/latest.json`; `releases/latest` ignores drafts and pre-releases (tags with a `-`).

## Building and running

Commands to build and run it (`npm ci`, `npm run tauri dev`): [setup.md](setup.md#launcher-build-and-test).

Linux needs the WebKitGTK stack (Arch: `webkit2gtk-4.1 gtk3 libsoup3 librsvg`; Debian: `libwebkit2gtk-4.1-dev libgtk-3-dev libsoup-3.0-dev libdbus-1-dev librsvg2-dev`), Node 22 and Rust. The result is `src-tauri/target/{debug,release}/poe2-launcher` plus deb, rpm and AppImage bundles. CI (Poe2Launcher, `.github/workflows/ci.yml`): Ubuntu runs `npm run check/test/build`, `cargo fmt --check`, `clippy -D warnings` and `cargo test`; Windows runs `cargo check`. The submodules are public and fetched by `actions/checkout`. Releases: see [Releasing](#releasing).

## One-time set-up

1. **Hook DLLs.** Nothing to set: the launcher downloads the **client hook** itself ([below](#client-hook)). Only if you want your own build (a developer), set Settings, *Hook DLL directory* to a folder holding `poe_hook.dll` and `poe_hook_core.dll`, normally `modules/client-hook/target/x86_64-pc-windows-msvc/release` (built with `build-dll`, [setup.md](setup.md#build-and-test)); it then wins over the download.
2. **Keyring (Linux).** Login tokens are stored only in the Secret Service (GNOME Keyring, or KWallet with its Secret Service interface switched on in System Settings). Without a provider the login is refused with an explanation, and the token is revoked again. Windows uses the Credential Manager.
3. **Linux:** Steam must be running when you press Play, and the Proton set in Settings (default `Proton - Experimental`) must exist under `<Steam>/steamapps/common`. The launcher only reads Proton from there.
4. **Server:** a server that has the web API on (`[web] enabled`, reachable from the player; use TLS outside a trusted network) and an account (`open_registration = true`, or `account create`).

## The flow

A fresh launcher shows a **Get ready to play** checklist at the top of the Play page (it disappears once all steps are done; the official mode has two steps, it has no server): **1. Install the game** (Library), **2. Get the client hook** (a *Download* button right there), **3. Host a server or join one** (*Create a server* downloads the server package and sets it up; *Find a server* opens the public list, *Add by address* the form). Nothing needs to be built, copied or configured by hand. The Play button says what is still missing and links to where to fix it.

1. **Servers:** *Add a server*, e.g. `127.0.0.1:8080` (`http://` is added, a pasted `/api/v1` is dropped), or *Add to my servers* in Browse. *Check* shows realm, ping, client version, players, whether registration is open and the game address.
2. **Log in** (in the server's card): *Log in* (`POST /login`, kind `launcher`, valid `[accounts] remember_days`) or *Create account* (only if registration is open; it logs in afterwards). *Log out* revokes the token on the server (and removes it locally even if the server is down, saying so).
3. **Library, Game:** your Steam account name and password, optionally *Remember the Steam login*. A Steam Guard code is typed into the launcher when Steam asks. The download is about 150 GB.
4. **Play** (the Play page) for the selected server once the game is installed and you are logged in.

## Play and news

**Play** is the first page (the official mode has it too). It keeps few things on screen:

- **The selected server**: name, a status light (*online / unreachable / checking*), players online, **ping** and who you are logged in as; click it to pick another saved server or *Manage servers...* (client version, uptime and the realm details are in the server's row on Servers). The ping is measured by the launcher: the time of its own `GET /api/v1/server` request (connect, TLS and answer). The status is looked at when the page opens, when you pick another server, every 30 seconds and on *Check* (Servers). A server on plain `http://` that you have not confirmed is not contacted.
- **The Play button** and one line under it: *Ready to play*, the starting step, *Game running*, or what blocks Play with a link to the page that fixes it (and *Switch to <version>* when the server wants another client). Play is only on this page.
- **The checklist** ([The flow](#the-flow)).
- **A server update notice** when you host a server and a newer release than the installed one exists: *Server update available (v0.3.0)* with a link that opens your server's panel on Servers ([below](#updating-the-server)). Nothing shows when you host nothing or are up to date.
- **The newest news item** as a link to the **News** page, which lists the news, newest first, cached (`<data>/poe2-launcher/cache/news.json`, fresh for 30 minutes, a manual refresh at most once a minute). Sources, all read without any login:
  - the **release notes** of the newest stable releases of `Distorbed678/Poe2Launcher` (tags `v*`), `Distorbed678/Poe2Server` (`server-v*` only; the other tags of that repository, such as `dat-schema-*`, are not news; the two older server releases that stay in Poe2ModdingProject are not shown) and `Distorbed678/Poe2ClientHook` (`hook-v*`), from the GitHub releases API (3 per repository);
  - **`news.json`** in the root of the hub repository (Poe2ModdingProject), `https://raw.githubusercontent.com/Distorbed678/Poe2ModdingProject/main/news.json`, hand-written announcements. Schema (`version` 1): `{"version": 1, "items": [{"id": "...", "date": "YYYY-MM-DD", "title": "...", "body": "...", "link": "https://..."}]}`. `id` is unique (`a-z A-Z 0-9 . _ -`, up to 64), `date` is `YYYY-MM-DD`, `title` is required (120 characters), `body` is optional markdown (4000 characters), `link` is optional and only `https` links are kept. A broken item is skipped, not the file; the file is limited to 256 KB. To post news, add an item at the top and push to `main`.
  - Offline, rate limited by GitHub or a missing file are quiet: the saved copy is shown (with "offline, saved 3 h ago"), a source that fails keeps its older items, nothing is a popup.
- **The server's message of the day** (on the News page, first in the list), when the selected server sends one: the optional `motd` text of `GET /api/v1/server` (see below).

**Safe rendering.** News bodies and the message of the day are markdown *subset* text: headings `#`..`###`, lists, quotes, code, `**bold**`, `*italic*`, `` `code` `` and `[text](https://...)`. They are rendered to plain text nodes, so HTML in the source (`<script>`, `<img onerror>`) is shown as text and never run. Only `https://` links become clickable, and they open in the system browser through the launcher (which refuses anything else).

**What the server has to send for the message of the day** (the launcher only reads it; the field does not exist on the server yet): an optional string `motd` in the JSON of `GET /api/v1/server`, for example `"motd": "Welcome!\nMaintenance on Saturday 18:00 UTC."`. Plain text with line breaks or the markdown subset above; the launcher keeps at most 2000 characters, drops control characters and shows nothing for an empty, `null`, missing or non-text value, so servers without it, and older servers, work unchanged. A natural place is a `[gateway] motd` config key, also settable from the web admin.

## Server browser

*Servers, Browse* shows the **public list of servers**, kept in the GitHub repository `Distorbed678/Poe2ServerList` (the repository's initial content, README and validator are in [../server-list-template/](../server-list-template/README.md)). The launcher reads `https://raw.githubusercontent.com/Distorbed678/Poe2ServerList/main/servers.json`.

- **The file** (`{"schema": 1, "servers": [...]}`): each entry has `id`, `name`, `address` (the web API address), `game_version` and optionally `description`, `region`, `tags`, `contact` and `mods` (required client mods: `id`, optional `version` and `url`); the full table is in the template's README and `servers.schema.json`. The launcher checks every entry again when it reads the file (it does not trust the list): a broken entry is skipped and counted ("1 list entry was ignored"), an address that is this computer or a local network is refused, a newer `schema` number is reported, the file is limited to 1 MB and 500 entries. The list is cached (`<data>/poe2-launcher/cache/serverlist.json`, fresh for 10 minutes; *Refresh* asks again), and an unreachable list shows the saved copy with a note.
- **Live status.** After the list is loaded the launcher asks every listed server itself, `GET <address>/api/v1/server` (no login, nothing else is sent), 12 at a time with a 3 s connect and 6 s total timeout, and shows players online, uptime, whether registration is open, the **ping** it measured and the client version the server reports (that answer, not the list's claim, is used for the filter). An unreachable server is marked as such.
- **Filter, search, sort.** By default only servers on your selected game version are shown (*Show other game versions too* lifts that; the official mode shows all). Search matches every word in name, description, region, tags, address and contact. Filters: region, tag, *Online only*. Sort: players (most first), ping (lowest first) or name; unreachable servers go last.
- **Add to my servers** creates a normal profile (name and address from the list) and checks it. A server listed on plain `http://` shows the plain-http warning with an "I understand" tick before it is added, like the Servers form ([below](#plain-http-warning)). Servers already in your list show *in your servers*. Required mods listed there are shown on the card; the launcher's mod sync works from what the server itself advertises ([Mods](#mods)).
- **How a host gets listed.** Run a server players can reach from the internet (use https for the web API), then send a pull request to `Distorbed678/Poe2ServerList` that adds an entry to `servers.json`; `python3 scripts/validate.py` in that repository checks it, and the repository's workflow runs the same check on the pull request. To change or remove the entry, send another pull request.

## Client hook

The hook is the pair of DLLs (`poe_hook.dll`, installed as the game's `version.dll`, and `poe_hook_core.dll`) that connect the game to a private server and, read-only, observe the official one. The **Client hook** card in the Library (Game tab) (and step 2 of the checklist) gets it from the releases of [Poe2ClientHook](https://github.com/Distorbed678/Poe2ClientHook) (tag `hook-v<version>`, made by that repository's CI: [releasing-hook.md](releasing-hook.md)):

- **Which release.** The newest stable release (a pre-release only when nothing stable fits) whose package supports the selected game version (from the version dropdown; *Official (read-only)* uses the newest private version's hook, the same DLLs run in official mode). The package name carries the game versions: `poe-hook-v<version>-game-<game versions>-windows-x86_64.zip`.
- **Checks.** The zip against the release's `.sha256` (and its size), then safe unpacking (no paths outside the folder, no links, bounded size), then `release.json` (schema, `windows`/`x86_64`, both DLLs listed, only safe paths), then **every file against the size and SHA-256 in `release.json`, with no unlisted file allowed**, and the game version against the one selected. A failure deletes everything; nothing is installed. The same files are hashed again right before each Play (a changed DLL stops Play with "download it again").
- **Where.** `<data>/hook/packages/<hook version>/`; Play deploys from there automatically. A newer release replaces the older one of the same game versions; a hook kept for another game version stays. Downloads go to `<data>/hook/downloads/` and are removed.
- **The card** shows the installed version, the game versions it serves and the mod ABI, whether an update is available (looked up once at start and on *Check for updates*) and a *Download client hook* / *Update* button. Offline or rate-limited GitHub is a message on the card, never a stop for a hook that is already installed.
- **Override.** Settings, *Hook DLL directory* (advanced) stays: when set it wins over the download (the card says "your own build"). Files in the old default folder `<data>/hook-dlls` are still used when nothing is downloaded and no directory is set ("files copied by hand").

Without a hook Play is blocked with "Get the client hook first (Library)". The download shows its speed and the time left.

## Game versions and the official mode

The version picker at the top of the sidebar lists every target the launcher can work with. The list comes from the embedded `modules/protocol/versions/<version>.toml` files (one per supported client build, copies of Poe2Protocol's files, [new-game-version.md](new-game-version.md#the-launcher-and-the-version-dropdown)), so a second supported build appears as a second entry without any UI change. The choice is saved in the launcher's `settings.json` (`game_version`; empty or a version this build no longer knows means the newest) and survives restarts. It cannot be changed while the game is being downloaded, starting or running, or while the hosted server runs.

What follows the selection:

| Part | Private version `<v>` | Official (read-only) |
|---|---|---|
| Install folder | `<data>/game/<v>` or the folder set for that version in Settings (each version has its own) | `<data>/game/official`, separate from every private version |
| Download | the depots with the pinned manifests of `modules/protocol/versions/<v>.toml` | the same depots **without manifests**: the current official build |
| Verify | file counts, key file sizes and the exe checksum of that version file | the main files exist and the size floors (the build is not pinned) |
| Play | the selected server profile, auto-login token, `mode = "private"` | no server, no token, `mode = "official"` ([below](#official-read-only)) |
| Servers, Account, Host a server, Mods | available; a server that reports another client version is marked *incompatible* | hidden (these are for private versions) |
| Host a server | downloads the `poe-server` package whose name carries this game version | not possible |
| Client hook | the newest hook release whose package supports `<v>` | the newest private version's hook, run in official mode |

**Server compatibility.** *Check* (and a quiet check at start) reads `GET /server`. A server whose client version equals the selection is *compatible*. A server that reports another version this launcher supports shows *needs client X* with a one-click *Switch to X*, and Play is blocked for it. A server reporting a version the launcher does not know is marked *incompatible* with a warning; Play is not blocked then (the check can be wrong).

### Official (read-only)

For observing a session on the official servers, exactly what `cargo xtask deploy-client --official` does for a developer ([official-mode.md](official-mode.md)); read that page's risk section first. Selecting it and pressing Play:

1. asks once for the warning to be accepted (the risk text of official-mode.md and an "I understand" box; saved as `official_ack`; the backend refuses to start without it too);
2. deploys the hook with `mode = "official"`, `login_mode = "steam"`, an **empty** `trusted_servers`, the original `gateway_list.txt` put back from `gateway_list.txt.orig`, no position sync port and no output folder. The launcher never writes a trusted server or a private gateway for this mode, and the hook's read-only latch is not touched;
3. starts the game without the standalone-login argument, with its own Steam login (Linux: through Proton in a **separate** prefix `<data>/proton-prefix-official`, so no private login or realm choice leaks into it; Steam must be running). The launcher sends nothing to any server and logs in nowhere.

If the game was updated and the hook's signature table does not match the new build, the hook switches its features off by itself (the log line says `NOT verified`): expected, the game just runs without the observer. The unit tests cover the deploy files (official versus private) with a temporary game folder; it has not been played against the official servers from the launcher.

The Steam download for the official build is the same Library (Game) page; *Download again* updates to whatever Steam currently serves, *Repair* re-checks files.

### Install in detail

The version file (the selected version's) is `modules/protocol/versions/<version>.toml` of Poe2Protocol (the single definition of a supported build; the launcher embeds a byte-identical copy that `cargo xtask versions` keeps, see [new-game-version.md](new-game-version.md)). For 0.5.5e: app 2694490, depot 2694491 manifest 7366357142270402355 (content), depot 2694492 manifest 246779027001700092 (Windows exe), in that order into one directory (exe over content).

- **DepotDownloader 3.4.0**, the self-contained release (no .NET), is fetched from its GitHub release into the launcher's data directory, pinned by version and SHA-256 (`versions/depotdownloader.toml`); a mismatch deletes the download.
- It runs **once for both depots** (`-app 2694490 -depot 2694491 -manifest ... -depot 2694492 -manifest ... -username U -dir DIR`), so the Steam login and Steam Guard code are asked once. `-no-mobile` is added by default so a typed code is requested instead of the mobile-app confirmation (Settings). `-remember-password` is added only if you tick the box (then DepotDownloader keeps its own login token; the launcher still never stores the password).
- **Remembered Steam login and *Log out of Steam* (Settings).** DepotDownloader 3.4.0 keeps the token in `account.config`, in .NET's isolated storage (`<local data>/IsolatedStorage/<id>/<id>/Url.<hash>/AssemFiles/account.config`). On Linux the launcher starts it with `XDG_DATA_HOME=<data>/steam-login`, so that file lives in the launcher's own data folder; *Log out of Steam* (with a confirmation) deletes it and clears the saved account name and the *remember* switch. The Settings card says *Logged in as X* or *Not logged in*. On Windows .NET asks the system for the folder (no environment override), so the file is under `%LOCALAPPDATA%\IsolatedStorage` and only files named `account.config` at the isolated-storage depth are removed (that also logs out any other DepotDownloader the same Windows user runs). Never the Steam client or its files. A login remembered by an older launcher version sits in the shared `~/.local/share/IsolatedStorage` and is not used any more (type the password once; delete that old file by hand if you want).
- **The Steam password** is typed in the launcher, written once to the downloader's standard input when it asks for it, then wiped from memory. It is not on a command line, not logged, not saved. Steam Guard prompts are detected in the output (they have no line end) and shown as a code box.
- **Never the Steam install.** The launcher does not read or write `~/.local/share/Steam/steamapps/common/Path of Exile 2` or `compatdata/2694490`; an install directory inside any Steam library is refused. The default is `<data>/poe2-launcher/game/<version>` (`~/.local/share/poe2-launcher/...`), one folder per game version.
- **Pause and resume.** *Pause* stops DepotDownloader (the process is killed; what it has written to disk stays) and the page shows *Paused*; *Resume download* runs **the same command line again with `-validate`**, so DepotDownloader checks the files that are on disk and fetches what is missing or incomplete, and at the end the install is verified as usual. The password is never kept: Resume asks for it again unless the Steam login is remembered. Pause survives leaving the page but not closing the launcher (start the install again then; the files on disk still count). *Forget the pause* drops it. This follows from how DepotDownloader works and is covered by a test with a fake downloader; it has not been run against Steam yet.
- **Speed and time left.** The depot progress lines (`NN.NN% file`) are converted to bytes with the estimated size of each depot (the exe depot is the exe's size, the content depot the rest of the estimated install) and averaged over the last 15 seconds: *Total (estimate)*, MB/s, time left, bytes done. The numbers are estimates because DepotDownloader prints percentages, not byte counts; after a resume they restart from the validation pass.
- **Disk space.** Before every install or repair the launcher compares the free space of the disk of the install folder (the nearest existing folder, if the target does not exist yet) with what is still missing: the estimated size (the version file's `[verify] min_bytes`, a floor measured on a full install, plus 16 %: about 174 GB for 0.5.5e) minus what is already in the folder. Not enough: the buttons are disabled and the page says how much is needed, how much is free and how much to free up; the backend refuses the same way. An unknown size or an unreadable disk does not block.
- **Verification** afterwards (and on *Verify files*): file count and total size floors, key files with exact sizes, SHA-256 of `PathOfExileSteam.exe`. **The reference values were measured on the `GameFiles/` copy in this repository, not on a launcher download**, so they are unconfirmed: the executable checksum is a warning (not a failure) until `exe_sha256_enforce = true` is set after the first real install matched. *Repair* re-runs the download with `-validate`.

### Play in detail

1. `GET /server` gives `login_host`, `login_port` (the public one), `instance_port` and `gateway_region`. If the server still advertises loopback while the launcher reached it elsewhere, the address the launcher used is taken.
2. `POST /api/v1/game-token` exchanges the launcher token for a one-off `game_remember` token. The launcher token itself is **not** written for the game: the game's login retires a token when it uses it (rolling tokens, [../architecture/accounts.md](../architecture/accounts.md#tokens)), which would log the launcher out.
3. `write_login_token` puts the 32-byte token and `[LOGIN] username=<account>, save_login=true` where the client reads its Remember Me ([../re/standalone-login.md](../re/standalone-login.md), section 4). The client logs in on its own when it starts.
4. `deploy` writes `gateway_list.txt` (one entry for this server), installs `version.dll` and `poe_hook_core.dll`, sets `poe-hook.toml` (`mode = "private"`, `login_mode = "standalone"`, `trusted_servers` = the server's login and instance `host:port`) and writes `steam_appid.txt`. Private mode for a private version; the official mode has its own deploy ([above](#official-read-only)).
5. Start: Linux `proton run PathOfExileSteam.exe --success-event 0` with the launcher's own prefix (`<data>/proton-prefix`, created with `proton run wineboot -u` on first use; crash dumps are set aside as in `run-client`); Windows runs the exe directly. Output goes to `<data>/logs/game-<time>.log`.
6. **Minimize while playing** (Settings, off by default): when on, the launcher window minimizes when the game process starts and is shown and focused again when it ends (only if the launcher was the one that minimized it).

## Window, icon and desktop entry

- **Frame.** The window has no system decorations: the launcher draws a thin strip along the top with minimize / maximize-restore / close (drag the strip or the sidebar's brand to move, double-click to maximize; the update badge is at the foot of the sidebar) and eight resize handles on the edges. It is square with a 1 px border: a transparent window with rounded corners was tried and did not paint reliably under WebKitGTK on Wayland (parts of the page stayed empty), so it is not used. Settings, *Use the launcher's own window frame*, switches to the system title bar and borders if the custom frame misbehaves on your desktop.
- **Icon.** An original mark (a glowing doorway under an arch with a keystone rune; source `modules/launcher/assets/icon.svg`, generated sizes in `src-tauri/icons/` with `npx tauri icon assets/icon.svg`). Windows uses `icon.ico`. It contains nothing of Path of Exile or Grinding Gear Games.

## Host a server

The **hosting panel** runs a private server on the machine you play on. It slides in over the Servers page: **Create a server** opens it while you host nothing, and then it shows three steps (*Program*, *Settings*, *Start*) and follows the next open one; once the server is set up, **Manage** on its row opens it with five tabs (*Overview*: run state and the live log, *Program*, *Settings*, *Log*, *Backups*). In *Settings* the ports, the cluster id, remote login through the web API and the port-forwarding list are folded under *Advanced*. It is WP F2 of [../plans/orchestration-2026-10b.md](../plans/orchestration-2026-10b.md); the package it uses is made by the server release CI ([releasing-server.md](../../modules/server/docs/releasing.md)). Hosting works on Linux and Windows. Everything the panel does is also listed, with the code, in the launcher README.

1. **Server program.** *Download the latest release* asks the GitHub releases of `Distorbed678/Poe2Server` for tags `server-v*` and takes the newest stable release whose package is named `poe-server-v<ver>-game-<your game version>-<linux|windows>-x86_64.tar.gz` (Linux) or `.zip` (Windows). Only when that repository has no fitting release (or cannot be read) the launcher asks `Distorbed678/Poe2ModdingProject`, which still holds the two earliest releases (`server-v0.1.0`, `server-v0.2.0`); the release list shows which repository a release came from. The `.sha256` file of the release is read first, the archive is downloaded, and its SHA-256 must match or the download is deleted and nothing is installed. GitHub answers 404 for a repository that is private or has no releases: the page then says so and points to the alternative. *Use a package file...* or *Use a package folder...* takes a package you have: an archive (checked against a `.sha256` file next to it when there is one, otherwise installed with a note that it was not checked) or an unpacked package folder (copied). Both routes check the package itself: `release.json` must say your OS and the game version your launcher installs, and the files the server needs from its own folder must be there (`poe-server`, `config/server.example.toml`, `third_party/dat-schema/schema-poe2.min.json`, `modules/protocol/opcodes/` and the version file of your game version, which is `modules/protocol/versions/<game>.toml` in Poe2Server packages and `versions/<game>.toml` in the two old ones: both layouts are accepted). Archives are unpacked with path, link and size checks. The package lands in `<data>/poe2-launcher/server/packages/<name>`; an older package is removed after a newer one is installed, the database stays (it lives in `<data>/poe2-launcher/server/data/`). No game files are in a package. Once a server is installed the button is *Check for updates* and the update flow below applies.
2. **Set up.** The form asks for:
   - the **server name** (shown to players, and the name of the profile that is added to Servers) and the **cluster id** (login tokens are bound to it);
   - the three **ports**: login (TCP), game (TCP and UDP, the client hook's side channel uses the same number) and web (TCP, the web API and the web admin). The page refuses ports that something else already uses;
   - the **public host**, the address players use to reach this computer: *Use my LAN address* fills in the address of the interface your default route uses (nothing is sent to find it); *Look up my public IP* asks `api.ipify.org` and happens **only when you press that button**. The page lists the ports to forward in a router for players outside your network and links to [hosting.md](../../modules/server/docs/hosting.md);
   - **open registration** (anyone can create an account) and whether the **web API is reachable from other computers** (binds `0.0.0.0` instead of loopback; it is plain http, see [hosting.md](../../modules/server/docs/hosting.md#tls-reverse-proxy-for-the-web-api));
   - the **admin account**: a name and a password (at least 8 characters, typed twice).

   *Set up and start* writes `config/server.toml` into the package folder from the package's own `config/server.example.toml` (only these keys change: `game_dir` = the launcher's installed game, `[network]` and the two binds, `[cluster] id`, `[gateway] display_name`, `[web]` enabled, bind and `static_dir = "web-admin"`, `[accounts] open_registration`, `[database] path` below the launcher's folder; every comment and other key stays), then creates the admin (see below), starts the server, waits until its web API answers, adds the profile `http://127.0.0.1:<web port>` to Servers and logs in with the new account. The game must be installed first (Install page): the server reads its data from there. Later the same form is *Apply settings* (the server must be stopped); an empty password keeps the accounts as they are.
3. **The admin account.** A password must never be on a command line (any user of the machine can read it in the process list), so the launcher uses the server's own offline commands and gives the password on standard input: it runs `poe-server account create <name> --password-stdin` in the package folder with the new `config/server.toml` (the password is written to the child's standard input as one line, then the pipe is closed and the launcher's copy is wiped), and then `poe-server account role <name> admin`, which carries no secret. Both commands work on the database directly; **the server is not started** for this (the setup used to start it once, privately, with a loopback config and open registration; that path is gone). If the name already exists the create step reports it, and the account is just promoted and its password stays. A password with a line break is refused. The password is not stored, not in the config, not in the log, not in an environment variable, and not in the process list.
4. **Run.** *Start* and *Stop* (a stop is SIGTERM on Linux, which the server answers with a graceful stop: players are disconnected, sessions saved, about 5 seconds; the launcher waits **15 seconds** before it kills the process; on Windows it is a hard stop), the state (starting while the game data loads, running when the web API answers, the number of players online), *Start this server when the launcher starts* (autostart), and the **server log**: the process's standard output and error, shown live (the last 2000 lines), also written to `<data>/poe2-launcher/server/server.log` (replaced at each start). **The server runs while the launcher is open; closing the launcher stops it.** A server that ends by itself is shown as stopped unexpectedly with its exit code and the last log lines.

   **Restart from the web admin.** The generated `config/server.toml` has `[server] restart_mode = "exit"` ([server-admin.md](server-admin.md#stop-and-restart-the-server)): when an admin restarts the server from the web admin it shuts down gracefully and exits with **code 75**. The launcher sees that code (and that it did not ask for a stop), writes "the server asked for a restart" to the log and starts the same server again with the same configuration and log file (the state stays *running*, with the new process id). More than 3 such restarts within 30 seconds are a crash loop: the launcher gives up and shows the exit code. A stop from the web admin exits with 0 and the server stays stopped. A server set up by an older launcher keeps `restart_mode` at its default (`exec`), which works on Linux; apply the settings once on the page to write the new key (needed on Windows).
5. **Backups.** *Back up now* copies the server's database (`<data>/poe2-launcher/server/data/server.sqlite`: accounts and characters) into `<data>/poe2-launcher/server/backups/server-<UTC date>-<time>-<kind>.sqlite` with SQLite's online backup API, so the copy is consistent **while the server runs** (the file is then checked with `PRAGMA quick_check`; when the backup API fails and the server is stopped, a plain file copy is the fallback). The list shows date, kind (*manual*, *before start*, *before restore*, *before update*), size, **Restore** and delete. **Restore** needs the server to be stopped, asks for a confirmation, checks the backup with `PRAGMA integrity_check`, **backs up the current database first** (kind *before restore*, so a restore can be undone by restoring that one), then replaces the database (and removes the old `-wal`/`-shm` leftovers). *Back up automatically each time the server starts from the launcher* makes a *before start* backup just before the process starts and keeps the **last N** of those (1 to 100, default 5; manual, before-restore and before-update backups are never deleted automatically). The choices are in `<config>/poe2-launcher/backup.json`. Package updates keep the database and the backups.

### Updating the server

The launcher looks for a newer server release **when it starts, when the Play page or the hosting panel opens (at most every 10 minutes per game version) and on *Check for updates***. It compares the installed package's server version with the newest release for your game version in `Distorbed678/Poe2Server` (with `Distorbed678/Poe2ModdingProject` as the fallback described above); a prerelease counts only when no stable release exists. The check is one quiet request: nothing changes, a failure (offline, GitHub rate limit) is a line in the hosting panel and never a popup, and with no server installed GitHub is not asked at all. When there is a newer release the hosting panel (*Program*) shows **Server update available (v0.3.0)** with the release notes (the markdown subset, rendered as text) and an **Update to 0.3.0** button, and the Play page shows a notice with a link to it.

**Update** does, in this order (code: `host_update.rs`):

1. downloads the new package and checks its SHA-256 against the release's `.sha256` file **while the old server keeps running**: a bad download changes nothing and the server was never stopped;
2. stops the server gracefully when it runs (the same SIGTERM and 15-second grace as *Stop*; a confirmation is asked first because players are disconnected);
3. backs up the database with the backup feature (kind *before update*; it is kept until you delete it); if the backup fails the update ends here and the old server is started again;
4. unpacks the new package **next to** the old one (never over it) and checks it as above;
5. writes the new package's `config/server.toml`: it starts from the **new** `config/server.example.toml`, applies every setting you changed in the old `server.toml` (a value that differs from the old example, including edits made in the web admin's config editor, new sections and changed `[[leagues]]` lists), and then your answers from the hosting panel. Settings you never touched take the new release's defaults, so keys that are new in this release appear with their defaults and a changed default applies;
6. points the launcher at the new package and, if the server ran before, starts it again and waits until its web API answers (up to 90 seconds; a server that is still alive after that is taken to be loading). A server that stopped by itself at start counts as a failure;
7. only then deletes the old package folder.

**On any failure after the server was stopped, everything is put back**: the launcher points at the old package again, the new folder is removed, the database is restored from the step 3 backup (a *before restore* backup of the database as the new server left it is kept), and the old server is started again if it was running. The error on the page says what happened. The database and the backups live outside the package and are never part of the swap. A server that is stopped when you press *Update* stays stopped. The page is busy during the update, so a second update, a setup or a restore cannot start.

Players outside your network add your server as `<public host>:<web port>` (use https if you put a TLS proxy in front), install the game with their own launcher and play ([hosting.md](../../modules/server/docs/hosting.md#what-a-remote-player-needs)).

Settings are kept in `<config>/poe2-launcher/host.json` (no secrets). The package download shows its speed and the time left.

## Logs and crash dumps

*Library, Logs* lists, newest first, the **game logs** the launcher writes when you press Play (`<data>/poe2-launcher/logs/game-<time>.log`), the **hosted server's log** (`server/server.log`) and the **crash dumps** the launcher sets aside before the game starts so the client's helper never uploads them (`crash-dumps/`). Pick a file to read the last 3000 lines (at most the last 2 MB are read; ANSI colours are removed). *Search this log* highlights matches; *Only matching lines* and *Warnings and errors only* filter; lines with `error`, `fatal`, `panic`, `failed` or `crash` are red, `warn` lines yellow. A crash dump is binary: it is listed with its size and cannot be read here. The folder buttons open the log folder in the file manager. Files are read by an id the launcher itself listed, never by a path.

**Copy for a bug report** puts text on the clipboard and shows it below for a look: launcher version, OS, game version and whether it is installed, the client hook version, the server package, then the last 200 lines of the selected log. Before it is copied it is **redacted**: your home folder becomes `~` and your OS user name `<user>`, the account names the launcher knows (server accounts, the Steam account name, the host's admin) become `<account>`, values after `password`, `token`, `secret`, `authorization`, `Bearer` and similar keys become `<redacted>`, and any run of 32 or more hex characters (tokens, keys) becomes `<redacted-hex>` (a SHA-256 labelled as such stays). A log can still contain other private things: read it before you share it.

## Open web admin

On a server profile whose logged-in account is an **admin** (the Servers page shows an *admin* badge and the button, the account area of its card the role; the hosting panel has a button too), **Open web admin** opens the server's web admin in your system browser already signed in, without typing the password again.

- The role comes from the login (`POST /login` returns the account with its role) and is re-read with `GET /api/v1/me` when you press *Check*, when the launcher starts, and every time you press the button, so a promotion or demotion shows without logging in again.
- The button asks `POST /api/v1/web-token` (launcher token of an admin only; the server answers with a single-use token valid for `[web] web_token_ttl_secs`, 60 seconds by default) and then opens `<server address>/#/token-login?t=<token>` with the Tauri opener. The token travels in the URL fragment, which the browser never sends to the server; the web admin removes it from the address bar and redeems it once ([../architecture/web-api.md](../architecture/web-api.md#opening-the-web-admin-from-the-launcher)).
- The launcher checks that the link the server returned is exactly that form, with the token it was just given, before it opens anything; it never logs the link. A player account, an old server without the endpoint, a refused request and a missing browser each give their own message and open nothing.

## Plain http warning

A password or login token sent over `http://` can be read by anyone on the way (audit finding S-03, [../plans/public-release-audit.md](../plans/public-release-audit.md)).

- To **this computer** (`localhost`, `127.0.0.1`, `::1`) plain http is fine and needs nothing.
- To **any other address** the launcher shows a warning when you add or edit the server (a checkbox *I understand* is required before it saves) and, for a server that was added earlier, a notice on the server's card (Servers) with *I understand, allow plain http for this server*. Until you agree for that address the launcher sends nothing there: no log in, no register, no token for Play or the web admin. The backend enforces this, not just the UI. The agreement is per address: changing the address withdraws it.
- A bare `host:port` you type gets `http://` when it is this computer or a local network address (192.168.x.x, 10.x.x.x, 172.16-31.x.x, `*.local`, single-label names) and `https://` for everything else. An explicit `http://` is kept.
- The server you host from the launcher uses plain http on loopback. If you open its web API to other computers, put TLS in front ([hosting.md](../../modules/server/docs/hosting.md#tls-reverse-proxy-for-the-web-api)) and use the `https://` address in the players' launchers.

## Releasing

A release is a pushed tag; `.github/workflows/release.yml` of Poe2Launcher does the rest.

1. Set the same new version in `src-tauri/tauri.conf.json` (`version`), `src-tauri/Cargo.toml` and `package.json` (and `src-tauri/Cargo.lock` follows from a build), commit and push to `main`. The workflow refuses a tag that does not match all three.
2. Tag and push: `git tag v0.1.1 && git push origin v0.1.1` (in the Poe2Launcher repository). A tag with a `-` (`v0.2.0-rc1`) makes a pre-release, which the update endpoint ignores.
3. The workflow (a) checks the secrets and the version, (b) creates a **draft** release with notes generated from the commits since the previous release, (c) builds on `ubuntu-22.04` (`tauri build --bundles appimage`, so the AppImage runs on distributions back to that glibc) and `windows-latest` (`--bundles nsis`) with `tauri-action`, which signs the updater artifacts, attaches the AppImage, the `.exe` installer, their `.sig` files and a merged `latest.json`, and (d) publishes the release only when `latest.json` lists both `linux-x86_64` and `windows-x86_64`. A failed job leaves a draft; delete the draft and the tag, or re-run the failed jobs.
4. Nothing is pushed or released from a developer machine. To test locally what CI does: `TAURI_SIGNING_PRIVATE_KEY="$(cat ~/.tauri/poe2-launcher.key)" TAURI_SIGNING_PRIVATE_KEY_PASSWORD="$(cat ~/.tauri/poe2-launcher.key.password)" npx tauri build --bundles appimage` in `modules/launcher` gives `src-tauri/target/release/bundle/appimage/*.AppImage` and `.AppImage.sig` (do not commit the outputs). The NSIS installer cannot be built on Linux without `makensis`: `cargo xwin build --target x86_64-pc-windows-msvc` (with `third_party/cargo-xwin`, `XWIN_CACHE_DIR=third_party/xwin-cache`) compiles the Windows binary as a check, the installer is CI-only. The workflows can be linted with `third_party/actionlint/actionlint` (downloaded by `third_party/fetch-tools.sh`).

**Secrets** (repository secrets of Poe2Launcher; the release workflow fails at once if one is missing):

| Secret | What | How it is made |
|---|---|---|
| `TAURI_SIGNING_PRIVATE_KEY` | the updater's private signing key (minisign format, the file's content) | `npx tauri signer generate -w ~/.tauri/poe2-launcher.key -p "$(cat ~/.tauri/poe2-launcher.key.password)"` once, in `modules/launcher`; then store the content of `~/.tauri/poe2-launcher.key` as the secret |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | the key's password | a random string kept in `~/.tauri/poe2-launcher.key.password`; the same file's content is the secret |

Set them with `gh secret set TAURI_SIGNING_PRIVATE_KEY < ~/.tauri/poe2-launcher.key` and `gh secret set TAURI_SIGNING_PRIVATE_KEY_PASSWORD < ~/.tauri/poe2-launcher.key.password` (the project owner does this; the secrets are not created by the tooling). Nothing else is needed: the submodules (client-hook, protocol) are public and checked out with `actions/checkout`; the former read-only deploy keys and `SUBMODULE_TOKEN` were deleted on 2026-10-21 (WP D3).

**Key location and care.** The key pair was generated locally in `~/.tauri/` (`poe2-launcher.key`, `poe2-launcher.key.pub`, `poe2-launcher.key.password`, mode 600, outside every git repository). Only the **public** key is in the repository (`plugins.updater.pubkey` in `tauri.conf.json`). Back the three files up somewhere private: if the private key is lost, installed launchers can never be updated again (their embedded public key no longer matches; players would have to reinstall). If it leaks, generate a new pair, put the new public key in `tauri.conf.json`, release once more signed with the **old** key (so existing installs accept it and learn the new key), then switch the secrets. Never put the key or password in a file in a repository, an issue or a log.

**First real run (2026-10-21, WP E3).** Result: v0.1.0 and v0.1.1 were released by the workflow, and an installed v0.1.0 updated itself to v0.1.1 on Linux.

## Mods

Library, *Mods*: the mods a player runs, **per server**. The format is [../../modules/client-hook/docs/mod-manifest.md](../../modules/client-hook/docs/mod-manifest.md) (manifest v1 and v2, parsed by the shared `poe-hook-mods` crate); how to build one: [modding.md](modding.md). The hook's loader loads what the launcher puts into `<install>/poe-hook-mods/` and lists in `state.toml`, never in the official (read-only) mode, where the Mods tab is hidden.

**Sides.** Every mod has a badge: `client` (runs in the game), `server` (runs on a server) or `both` (one package, two halves). The launcher is for the client half: a **server-only** mod is refused ("it does not belong in the launcher's mod store", with the `poe-server mod install` hint), and from a `both` package only the client half is unpacked: the `server/` files never reach the player's disk. A mod with a DLL carries a *code* badge: it runs inside the game process with your user's rights (see the trust note in [modding.md](modding.md#client)).

**Cache and versions.** Everything you add or download goes to `<data>/poe2-launcher/mods/cache/<id>/<version>/` after `verify_package` accepted it (SHA-256 against the `.sha256` or the pinned hash, `<id>-<version>.zip` name, paths, links, size limits, CRCs, manifest; a failed check leaves nothing). Several versions of one mod live side by side. *Add package (.zip)* takes a package (a `.sha256` next to it is used; without one a warning says the identity is not pinned); *Add folder* a developer's mod folder (its identity is a hash over its client files).

**Per-server sets.** The *Mods for* picker above the list selects a server (or *All servers*). A server's **required** mods are always on for it, in the version the server pins. Your own mods are **off on a server unless enabled for it** (the checkbox), or enabled for all servers (*all servers*). Dependencies are pulled from the cache; an own mod that conflicts with a required one, is incompatible or lacks a dependency is left out with a note. **Play** copies the selected server's set from the cache into the game's `poe-hook-mods/` and writes `state.toml` (the load order: dependencies, `load.after/before`, then your arrangement); mods a previous server needed are removed from there. Folders in `poe-hook-mods/` that the launcher did not create (a developer's `deploy-mod`) are never touched and not enabled. A game-version mismatch can be overridden per mod; a mod ABI mismatch cannot (the loader would refuse it).

**Mod sync** (Settings, *Mods*: **Off / Ask / Auto**, default Ask). A server that requires mods says so in `GET /api/v1/server` (an optional field `mods`, next to `motd`; the server side of it is another work package, WP-M2): per mod `id`, `version`, `side`, `sha256`, `size`, `required`, `hook_api`, `game_versions`, `sources` and a display `name`, `authors`, `description`. The launcher compares that with its cache when you select the server and again before Play:

- **Off:** shows what is missing (Mods tab, the reason under Play) and **blocks Play** with an explanation; nothing is downloaded.
- **Ask:** pressing Play opens a dialog listing the missing required mods (name, version, side, size, *contains code*) with **Download**; Cancel stops Play. A failed download keeps the dialog open with the reason.
- **Auto:** downloads, verifies and switches silently and shows a toast. It includes code mods, also from a server you added a minute ago, without another question (the user's decision of 2026-10-22; use Ask if you do not want that).

Downloads come from the server itself (`/api/v1/mods/{id}/{version}.zip`) and then any extra `https://` addresses in `sources`; the package is kept only if its SHA-256 equals the advertised one and `verify_package` accepts it (the size is capped at the advertised size). A mismatch installs nothing. Plain `http://` to another machine needs the confirmation of the Servers page first (otherwise the server's own download path is not used). A required mod that is incompatible with your game version or hook ABI (or has no usable address) blocks Play in every mode with the reason; optional (`required = false`) mods are listed but never block. Servers without a `mods` field work as before. The check is advisory: the server may verify the client's mods at login, a modified client can still lie.

**Mod browser** (Mods, *Browse*). The community index is the file `index.json` of `Distorbed678/Poe2Mods` (initial content, schema and validator: [../mod-index-template/README.md](../mod-index-template/README.md)); the launcher reads `https://raw.githubusercontent.com/Distorbed678/Poe2Mods/main/index.json`, checks every entry (a broken one is skipped and counted), caches it (`<data>/poe2-launcher/cache/modindex.json`, 10 minutes) and shows the saved copy quietly when offline. Search by name, description, author or tag; filter by side, tag and "only for my game version"; pick a version (withdrawn and incompatible ones are marked) and **Install and enable** (for the server or *All servers* chosen above) or **Install only**. The download is from the entry's https `url` and must match the index's SHA-256 and size. Server-only mods are listed but not installable here.

**How to submit a mod to the index:** pack it with `poe-mod pack` ([Poe2ModSDK](https://github.com/Distorbed678/Poe2ModSDK)), publish the zip at a stable https address (a GitHub release asset), and open a pull request that adds an entry (or a `versions` item) to `index.json`; `python3 scripts/validate.py --online` checks the format and downloads the package. Steps and the field table: the template's README.

**Cache size.** Settings shows the cache size; *Clear unused cached mods* removes versions that no mod set enables and no server's last advertisement requires. A server's required mods are downloaded again when needed.

**Not tested against real servers.** The sync, download, per-server sets and index are covered by unit tests and tests against mock servers (tampered packages, Off/Ask/Auto, switching between two servers with different versions of one mod); no real `poe-server` advertises mods yet, the `Poe2Mods` repository does not exist yet, and nothing was played with a mod in the real game from the launcher.

## Testing the launcher against a local server

The real-server test needs a scratch server config (shifted ports, `open_registration = true`, an account made offline); commands: [setup.md](setup.md#launcher-build-and-test), config: [setup.md](setup.md#web-api).

The launcher's own tests already cover profiles with a mock keyring, login/logout/register and the whole Play preparation against a mock web API and a fake Proton; the plain-http guard and Open web admin against a mock web API (the browser is a recorder, nothing is opened); finding, downloading, verifying and unpacking server packages against a mock GitHub API; the server update against a mock GitHub API with fake packages (`tests/host_update.rs`: old to new update of a running configured server with the config carried over and the server started again, rollback when the new server ends at start with the database restored, a bad download and a failed backup that change nothing, the fallback repository, both package layouts, no request without an installed server); an ignored test downloads and starts the pinned DepotDownloader (never logs in).

**The client hook against the real release** (an ignored test, network only, nothing is deployed): `POE2_TEST_HOOK_REAL=1 cargo test --test hook_flow real_release -- --ignored --nocapture` in `src-tauri` lists the releases of Poe2ClientHook, downloads the newest one for the oldest supported game version into a temporary folder and checks the archive, `release.json` and every file.

**Hosting against a real server package** (an ignored test, no game client involved): build a package as in [releasing-server.md](../../modules/server/docs/releasing.md#checking-a-package-locally), then

```sh
cd modules/launcher/src-tauri
POE2_TEST_SERVER_PACKAGE=<out dir>/poe-server-v<ver>-game-0.5.5e-linux-x86_64.tar.gz \
POE2_TEST_GAME_DIR=<a game install, read only; the GameFiles/ copy works> \
  cargo test --test host_flow real_package -- --ignored --nocapture
```

It installs the package (checksum verified), sets it up in a temp launcher folder with ports 29500-29502 and a temp database (the admin is made by the one-shot `account create --password-stdin` and `account role` commands with a random throwaway password; the server is not started for it), starts it, waits for the web API, checks status, the log tail and `curl /api/v1/server`, logs in as the new admin (role `admin`), asks the real server for a web sign-in link (recorded, never opened), stops it and checks that the ports are free and the password is in no file. It takes about 15 seconds.

## End-to-end test on a real machine

1. Start the server with the web API and an account (above, or the real config).
2. Start the launcher in dev mode ([setup.md](setup.md#launcher-build-and-test)); set the DLL directory (Settings).
3. Servers: add the server; Account: log in.
4. Library, Game: enter your Steam account, answer the Steam Guard prompt, wait for "Done" and the verification table. Report any failed check; the warning on the executable checksum would mean the recorded value needs correcting.
5. Start Steam (Linux), press Play. Expected: the client opens on the realm and logs in by itself.
