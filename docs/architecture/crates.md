# Crates and servers

`modules/` holds git submodules, each its own Cargo workspace (or npm/Tauri project). The server is `modules/server` (Poe2Server): its crates and servers are listed below with their path in the hub; it has its own `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `target/` and CI, and builds on its own (`cargo xtask server build` from the hub). It carries Poe2Protocol, Poe2ClientHook and Poe2WebAdmin as nested submodules. The hub's own Cargo workspace is `xtask` only; it uses the server's `poe-config`, `poe-data`, `poe-world` and `poe-proto` (from the server's nested protocol checkout) and the hook's `poe-hook-deploy` and `poe-hook-sig` as path dependencies. `web-admin` (npm) and `launcher` (Tauri) are separate apps. Repository overview: [../overview.md](../overview.md).

| Crate | Role |
|---|---|
| `modules/server/crates/poe-config` | Typed `modules/server/config/server.toml`: ports, hosts, leagues, paths, logging, terrain toggle, cluster id, account switches, web API, commands, instances, movement tuning, terrain upload, dev tools (`modules/server/config/server.example.toml` lists every key), and `versions`: the parser of `modules/protocol/versions/<version>.toml`, the single definition of a supported client build (depots, exe fingerprint, opcode folder, signature table, accepted `client_hash` values, data anchors); `Config::load` attaches the file named by `[game] version` and fills `protocol_dir` from it ([../guides/new-game-version.md](../guides/new-game-version.md)). |
| `modules/protocol/poe-net` | Transport (Poe2Protocol submodule): `StreamCipher` trait (Salsa20 for login and instance streams), big-endian `Reader`/`Writer` with PoE string and varint encodings, hexdump; the buffered TCP `Connection` is behind the `tokio` cargo feature (the servers enable it, the client DLL does not). |
| `modules/protocol/poe-proto` | Message definitions (Poe2Protocol submodule); opcodes come from `modules/protocol/opcodes/<version>/{login,instance,hnc}.toml`. `describe` decodes captured messages for the DLL. |
| `modules/server/crates/poe-data` | Game data: `GameFiles` (Bundles2 through `poe_data_tools`, with override directories in front) and `GameData::table("WorldAreas")` (`.datc64` decoded with the community schema, columns accessed by name). |
| `modules/server/crates/poe-store` | `Store` trait plus SQLite: accounts, characters, saved positions; owns the schema migrations (`0006` adds passwords, roles and tokens). |
| `modules/server/crates/poe-accounts` | `AccountStore` trait and SQLite implementation: usernames, argon2id passwords (over the client's SHA-256(UTF-16LE) digest), roles, revocable per-cluster tokens, the `account` command. |
| `modules/server/crates/poe-mod-host` | The server mod host: the `mods/` folder (`state.toml`, folders, packages), load plan (manifest v2 via `poe-hook-mods`), native libraries (`libloading`, `poe-mod-api`), data-tier commands, events with read-only snapshots, submitted commands, the advertisement of client mods, the login comparison of the client's reported mods. [mod-host.md](mod-host.md) |
| `modules/server/crates/poe-cluster` | Coordination between servers: tickets (`TicketRegistry`), login sessions (logout, transfers), the instance directory (`InstanceDirectory`), `AdminControl` (what the web API needs from the instance server), `ModDirectory` (the offered client mods, packages and the mod list, implemented by the mod host). In-process implementations now; traits for a split deployment later. |
| `modules/server/crates/poe-web-api` | The HTTP/WebSocket API (axum): register, login, tokens, admin endpoints that run the command registry through `poe_cluster::AdminControl`, the live log layer, OpenAPI, static web admin. Started by `poe-server`. [web-api.md](web-api.md). |
| `modules/server/crates/poe-world` | Terrain generation (the client's generator, ported; see [../status/terrain.md](../status/terrain.md)). |
| `modules/server/crates/poe-game` | Simulation: the instance `World` (entities, frame clock), `GridSource` terrain grids (client dump `Grid`, `VecGrid`), the server-authoritative movement component `Locomotion` (typed inputs and events, no opcodes; built from [../protocol/movement.md](../protocol/movement.md)), `Mover` and A* pathfinding, character stats. Design: [instance-world.md](instance-world.md). Replay tests use fixtures under `tests/fixtures/` derived by `scripts/re/movement_fixtures.py`. |
| `modules/server/servers/login-server` | Login protocol: auth, leagues, characters, hand-off and transfers to instances. |
| `modules/server/servers/instance-server` | Instance protocol: areas, the instance actor (`actor.rs`: one task per instance owns the `World` and serves all its sessions), character blobs (`appearance.rs`), player handle, movement glue, chat, server commands (`commands.rs`, `exec.rs`), live sessions. |
| `modules/server/servers/poe-server` | Development launcher that runs the login server, the instance server and the web API in one process. |
| `xtask` (hub) | `cargo xtask` of the hub (commands: [../guides/setup.md](../guides/setup.md)): thin wrappers over `poe-hook-deploy`, the DLL name tables, `server` (`server.rs`: build, run with the hub as working directory, web admin rebuild), the generators for the README tracker (`tracker.rs`), the terrain matrix (`terrain_matrix.rs`), `check-build` (`check_build.rs`, `fingerprint.rs`: scans a game exe with `poe-hook-sig`, compares the opcode tables, strings and game data; report `dumps/<version>/check-build.md`) and `versions` (`versions.rs`: keeps the launcher's copies of the version files). `openapi` delegates to the server's own `xtask` (`modules/server/xtask`, the OpenAPI generator its CI checks). |
| `modules/web-admin` | Poe2WebAdmin submodule (Svelte 5 + Vite): the admin site on top of the web API, types generated from `modules/server/docs/openapi.json`. [web-api.md](web-api.md#the-web-admin-spa). |
| `modules/launcher` | Poe2Launcher submodule (Tauri 2 + Svelte 5, own Cargo workspace in `src-tauri`): server profiles, Steam depot install, deploy and start of the game, mods; nests Poe2ClientHook and Poe2Protocol. [../guides/launcher.md](../guides/launcher.md). |
| `modules/client-hook` | Poe2ClientHook submodule (own Cargo workspace): the client DLLs (Windows target: loader, debug core, shared config/ABI) and `poe-hook-deploy`, the host-side library behind `cargo xtask deploy-client`/`revert-client`/`deploy-core`/`run-client`. Nested submodule `protocol/` = Poe2Protocol. |

The server mod ABI (`poe-mod-api`) is in the SDK repository, pinned by git tag; the host that loads mods is `modules/server/crates/poe-mod-host`, see [mod-host.md](mod-host.md).
